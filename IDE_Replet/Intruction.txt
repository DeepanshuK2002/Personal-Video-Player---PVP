# PROJECT: NEXT-GENERATION INTERNET DOWNLOAD MANAGER

## 1. YOUR ROLE

Act as a senior software architect, C++ systems engineer, React developer, UI/UX designer, networking engineer, security engineer, and QA automation specialist.

Your mission is to design, develop, test, and package a complete, production-oriented desktop download manager inspired by the functionality of Internet Download Manager (IDM).

Build an original product with its own identity, architecture, and design language.

Do not merely create a frontend mockup. Every feature must be connected to real functionality unless explicitly marked as planned or unavailable.

Work autonomously on implementation tasks, inspect the existing project before modifying it, run available tests, diagnose failures, and verify your changes.

Do not attempt to implement the entire application in one enormous code-generation operation. Develop it incrementally, preserving working functionality throughout the process.

The primary target platform is Windows 11.

# 2. PRODUCT VISION

Create a modern, minimalist, high-performance desktop download manager that can eventually serve as a comprehensive alternative to Internet Download Manager.

The application should combine:

* A beautiful, professional desktop interface.
* A robust native C++ download engine.
* Parallel and segmented downloads where supported.
* Pause and resume functionality.
* Persistent download recovery.
* Download queues and scheduling.
* Browser integration.
* Bandwidth management.
* Detailed download information.
* Reliable error handling.
* Automatic updates.
* Optional AI-assisted features in the future.

The application must be designed for long-term development.

Prioritize reliability, performance, maintainability, security, and excellent user experience over unnecessary complexity.

Do not use proprietary IDM source code, assets, branding, or trademarks in a way that suggests an official relationship.

Create original branding and a distinctive interface.

# 10. SEGMENTED DOWNLOADING

Implement segmented downloads only after basic HTTP/HTTPS downloading is stable.

Use HTTP Range requests when the server supports them.

Before segmentation, inspect the relevant response headers and server behavior.

Account for:

* Range support.
* Known content length.
* Resource validators such as ETag or Last-Modified.
* Servers that ignore Range requests.
* Redirects.
* Changed resources.
* Expired authorization.
* Inconsistent range responses.
* Partial segment failures.

## Segment Management

Implement:

* Configurable segment count.
* Segment byte ranges.
* Segment progress.
* Independent segment retries.
* Thread-safe progress aggregation.
* Safe segment assembly.
* Cleanup after failure.
* Validation of segment boundaries.
* A fallback to single-connection downloading.

Do not assume every server supports parallel downloads.

Do not assume the same URL always represents the same file.

Validate response ranges and avoid combining segments from different resource versions.

Prevent overlapping writes and integer overflow when calculating byte offsets.

## Performance

Start with conservative concurrency defaults.

Allow users to configure connection limits within safe bounds.

Avoid creating an unbounded number of threads or network connections.

Measure actual performance before making optimization claims.
