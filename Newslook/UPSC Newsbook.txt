5. The important Telegram part

There is one important technical consideration.

If you control the source Telegram channel, the cleanest solution is:

Add your bot as an administrator

Then Telegram can deliver new channel posts to your backend.

Your listener receives something like:

NEW CHANNEL POST

Document:
The_Hindu_24_Sep_2026.pdf

File ID:
ABC123...

Message ID:
8492

The Bot API provides file IDs and file metadata, and getFile can be used to prepare a file for download.

However:

Telegram's standard Bot API currently limits bot downloads through getFile to 20 MB.

Newspaper PDFs can easily exceed that.

So I would not design Newslook around the assumption that every newspaper PDF is <20 MB.

If your PDFs are larger, we'd use a Telegram MTProto-based worker or another appropriate Telegram-supported retrieval architecture rather than making the mobile app deal with Telegram directly.

INGESTION PIPELINE

1. Detect new Telegram document.
2. Verify PDF/MIME type.
3. Record Telegram message/file identifiers.
4. Determine publication.
5. Determine edition date.
6. Prefer filename/caption/configured publication patterns.
7. Use PDF metadata if necessary.
8. Use OCR only as a fallback.
9. Calculate SHA-256.
10. Check for duplicate publication/date/hash.
11. Validate PDF.
12. Determine page count.
13. Create processing record.
14. Copy original PDF to BACKUP_PRIVATE_CHANNEL.
15. Create public archive/reference entry in BACKUP_PUBLIC_CHANNEL,
    subject to configured redistribution rights.
16. Upload original PDF to R2.
17. Generate cover thumbnail.
18. Insert/update D1 metadata.
19. Mark edition READY.
20. Expose edition through API.

The system must be idempotent.

Running ingestion twice for the same Telegram message must not create
duplicate editions.

RETENTION

Newslook live storage retains one year of editions.

Every day calculate:

cutoff = current_date - 1 year

Anything at or before the cutoff is expired.

Use two-phase deletion:

READY
→ EXPIRED
→ R2 DELETE
→ D1 DELETE

If deletion fails, retain a retryable failure state.

NEVER DELETE:

private Telegram archive
public Telegram archive
user cutouts
user highlights

The private Telegram channel is the permanent master archive.

28. One modification I'd make to the "free-only" recommendation

I would start on Cloudflare Free, but build the code so upgrading later requires almost no architectural change.

The current Workers Free plan allows 100,000 requests/day, and D1 has 5 million row reads/day and 100,000 row writes/day.

For a small early Newslook deployment, that's plenty of room.

But don't promise yourself that the entire service will remain free forever. The PDF storage is the likely first constraint: R2 currently gives 10 GB-month free, after which standard storage is $0.015/GB-month, while Internet egress remains free.

The good news is that your one-year retention policy dramatically controls that cost.

29. One more improvement: use Cloudflare Workflows for ingestion

For a simple MVP, a Worker is enough.

For the actual production pipeline, I'd structure ingestion as a durable workflow:

Telegram event
      ↓
Workflow
      │
      ├── Validate
      ├── Identify
      ├── Hash
      ├── Private backup
      ├── Public archive
      ├── R2 upload
      ├── Thumbnail
      └── D1 publish

Cloudflare Workflows supports multi-step durable execution and retries, and scheduled Workflow instances are now supported directly.

That is a much better fit than one giant Worker function.

The next implementation step should be the backend first, specifically:

Telegram ingestion → private backup → public archive → R2 → D1 → API

Once that pipeline is working end-to-end with one test newspaper, the Flutter app can consume it. That avoids building the UI against fake/static newspaper data and then having to redesign the backend around the app.
